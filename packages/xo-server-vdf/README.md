# xo-server-vdf

> Vates Distributed Firewall (VDF): REST routes for XO 6's Firewall screens

VDF is a stateful firewall in front of every VM, enforced by each host's `vdf-agent` with Open vSwitch connection tracking and driven by tags. The policy lives in the pool (`pool.other_config["vdf:policy*"]`), each agent reports what it enforces in its host's `other_config["vdf:status"]`.

This plugin never re-implements the agent's rules: validation, publication and traces go through the hosts' `vdf` XAPI plugin, which the agent installs.

## Tech preview: opt-in, and the off switch

Installed is not enabled: the plugin has a required setting, so xo-server leaves it unloaded until an administrator ticks **Enable the VDF firewall (tech preview)** in Settings > Plugins and loads it ([vdf#42](https://git.vates.tech/vates/vdf/issues/42)).

XO 6 shows the firewall only while `GET /rest/v0/plugins/vdf/info` answers, and the VM tab and Quarantine only in pools VDF manages: a host's agent wrote a status, or a policy is published (so a pool whose agents stopped or were removed still shows its VMs as exposed). Unloading the plugin is the off switch for XO: its routes and background sync stop, and the interface disappears within a minute. Policies already published stay enforced by the hosts' agents.

In XAPI, the plugin writes `vdf:*` keys of `pool.other_config`: `vdf:global.owner` itself, the `vdf:policy*` keys through the master agent's `publish`. The VDF lock (below) writes a VIF's allowed addresses and its `other_config["vdf:locking"]`, nothing else of the VIF. It never writes host or network `other_config`, nor tags: XO 6 tags VMs and networks through XO's own REST API, as any tag edit. `index.test.mjs` ("what the plugin writes in XAPI") checks the code and every route.

To stop enforcement too, without XO (from any host's shell, with the agent's own commands):

- **A pool:** `vdf-agent unpublish` with no argument, on any host of the pool, removes every `vdf:policy*` key of `pool.other_config` in one write. Each agent drops its VDF flows within a second (at once when `vdf:policy` is empty, as XO writes it; otherwise after enforcing `vdf:policy` for a 3 s grace), and forgets its last valid policy, so the policy doesn't come back. In the global configuration's scope, that doesn't switch the pool off: while this plugin is loaded, the global sync writes the pool's global part back within about 5 s, without the pool's own policies, and the pool then enforces the global policies alone. To switch a pool off fully, take it out of the global scope first (or unload this plugin). The unpublish shows as a change outside this XO in the pool's history, and the previous entry restores the pool's own policies.
- **A host:** `systemctl stop vdf-agent`, then `vdf-agent clear`, which removes the VDF flows, port flags and MAC pins from the host's bridges and its status. A stopped agent alone leaves the last flows in place.
- **Quarantine** follows the `vdf:quarantine` VM tag, whatever the pool's document: an unpublished pool still cuts its quarantined VMs off, and agents cut them off again when they start, as long as the tag stays. Remove the tag, or stop and clear the agents.

XO has no off switch of its own yet beyond unloading the plugin ([vdf#42](https://git.vates.tech/vates/vdf/issues/42)).

## Routes

Under `/rest/v0/plugins/vdf/pools/{id}`:

| Route                         | What                                                                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GET policy`                  | The document the pool enforces (the newest pool key whose base still matches, as agents choose it) and its id              |
| `POST actions/check_policy`   | `{ policy }`: validate with the pool master's agent, nothing written                                                       |
| `POST actions/publish_policy` | `{ policy, expectedDocId? }`: validate and publish, as `vdf-agent publish` does (see below)                                |
| `POST actions/trace`          | `{ from, to, proto, port?, state? }`: why is this blocked? One hop per host involved, as `vdf-agent trace` orchestrates it |
| `GET stats`                   | Per host: rule hit rates, open connections with the rule that let them in, blocked attempts                                |
| `GET rule-log`                | Entries of every host's per-rule audit log, oldest first (`lines`, `since`)                                                |
| `GET history`                 | The last documents XO published to the pool, oldest first, without their content                                           |
| `GET history/{entry}`         | One of them, with the version it replaced (`previous`, when kept)                                                          |

**Concurrent edits:** with `expectedDocId` (the id of the document the edit started from, `''` for none), a publish is refused with `conflict: true` and nothing is written if the pool's document changed meanwhile. Publishes through XO are serialized per pool, so two of them cannot both pass the check; a write made in between by the global configuration or outside XO (`vdf-agent publish`) makes the check fail, which is the point.

## Global configuration

Groups and policies defined once in XO and written into every pool in scope (all pools, or a list), next to each pool's own (`global.mjs`). Agents only ever see their pool's document, so a pool keeps enforcing its last document whatever happens to XO or to the other pools.

- **Supported deployment** ([vdf#30](https://git.vates.tech/vates/vdf/issues/30)): one XO governs the global configuration, and every pool that takes part in global groups is connected to it. Several XOs may manage a pool's own policies: they share the pool's document, and each one sees the others' publishes as changes outside it (see History). Federation between XOs isn't planned.
  - Members of global groups only come from the pools this XO is connected to. A VM in a pool that only another XO manages never counts: "apps of pool 3 may reach the databases of pool 1", with pool 3 on another XO, silently matches nothing from pool 3.
  - A pool connected here, in this XO's scope, but holding another XO's global part (`other-xo`) still adds its VMs to this XO's global groups, while never getting this XO's configuration: one way, and a tag changed from that XO changes what matches here. `GET /global` marks those members with `otherXo` (that XO's name), and XO 6 shows it on them in the global overview. Take the pool over, or leave it out of the scope.
- **Ownership in a pool's document:** XO owns every group and policy named `global:*` and the rule ids from `0x800000` up (agents refuse unknown fields, so names carry the origin). Pool routes rewrite that part on every check and publish: a pool's edit can't change it, and a pool's own rule ids must stay below that range.
- **Order:** global policies come first in the document. Agents take a tier's policies in document order, so in a tier shared with the pool's own policies, global rules match first. A global policy in the baseline tier sets defaults the pools can override.
- **Tiers kept for global policies** ([vdf#21](https://git.vates.tech/vates/vdf/issues/21)): tiers decide in order whoever wrote the policies in them, so a pool's own allow in `emergency` would decide before a global drop in `securityops`. In a pool the global configuration applies to (in scope, or holding another XO's global part), the pool's own policies may not use the tiers up to `securityops` (`emergency`, `securityops`, numbered tiers up to 25): pool checks and publishes refuse them, and XO 6 doesn't offer them there. A global policy in an earlier or the same tier therefore always wins. Pools out of scope keep every tier; global policies use any.
  - A global publish that brings a pool into the scope while its own policies use those tiers is refused for that pool (`reservedTiers` lists them, nothing is written anywhere): it would claim a guardrail the pool doesn't have. Move them to `networkops` or a later tier first.
  - A pool can still end up in scope with some (connected later under "all pools", unreachable at the publish, or edited outside XO): XO writes the global part anyway, since it only adds to what the pool enforces, reports the pool's `reservedTiers` in `GET /global` and as a warning at the next global publish, and the pool can't publish its own part until they're moved.
- **Members across pools:** each pool's agents resolve tag groups from their own VMs. For every global group, XO adds the IPs of its running members in the other pools in scope, per VIF as agents count them: a locked VIF's allowed addresses, else what the guest reports for that VIF's device, nothing for a disabled VIF. Addresses the guest reports for a device the VM has no VIF for count nowhere: the guest writes those keys itself, and a fully locked VM could otherwise add any address to its groups, which XO would write into every other pool (the agent's own fix, vdf b6846f8; XO followed in vdf#36).
- **Addresses held twice:** a member's IP that another running VM (any pool) holds too is left out of the other pools at once, and reported in `conflicts`: they couldn't tell the two VMs apart. The same IP on VMs of two pools in scope is reported in `overlaps`: members across pools only make sense if the pools share a routed address space.
- **A pool XO loses** keeps its members in the other pools, with their last known IPs (fail static), as long as XO still has the pool's server; members are dropped once the server is removed from XO. Key `vms` of the store: the running VMs of each pool when XO last saw them. The pool shows as unreachable, its members as `stale`.
- **One XO per pool:** the XO that writes a global part into a pool (once the write succeeded) records itself in `pool.other_config["vdf:global.owner"]` (`{ id, name, since }`, id kept in the store's `instance` key). Another XO then leaves that pool's global part alone: its sync skips the pool, its global publishes report it (`otherXo`) without failing, and its pool routes keep that global part as is. `POST /pools/{id}/actions/take_over_global` makes this XO the owner.
- **A restored or copied XO keeps its own identity** ([vdf#20](https://git.vates.tech/vates/vdf/issues/20)): importing a config export never adopts the exported `instance`, so an export restored on a second XO while the first one runs (upgrade test, staging copy, DR rehearsal) can't make both write the same pools. The import keeps (or creates) this XO's own id, takes the global configuration, histories and syncs, and records the exported XO in the store's `replaces` key (`{ id, name, importedAt }`, reported by `GET /global`); importing this XO's own export changes nothing. The pools that XO owns show as `other-xo` until an administrator takes them over: `POST /global/actions/take_over_replaced` (Global firewall > Overview, "Take over its pools") runs one `take_over_global` per pool, expecting that XO as the owner. That's the only way another XO's pools become this one's. A copy of XO's whole data directory (a VM clone) still shares the identity: XO has no install id to tell the copies apart.
- **Publish:** every pool in scope (and every pool still holding a global part) checks its new document with its master's agent. Nothing is written unless every reachable pool accepts it. Pools XO can't reach are reported and catch up later. `revision` is required (0 for the first publish): from an older one, the publish is refused with `conflict: true`, as a pool's. A scope naming a pool XO doesn't know is refused. The configuration is saved before the pools are written: a pool whose write fails makes the publish `partial` (no rollback), and is retried 5 s later.
- **One write path:** global publishes, the sync and pool publishes write a pool one at a time (per-pool lock), each composing from what the pool holds at that moment and re-reading its owner: a pool publish is never undone by a sync that read the pool before it. XAPI has no compare-and-set on `other_config`, so a window as short as the agent's call remains against writers outside this XO.
- **Sync:** XO follows its object events (throttled to one pass every 5 s, plus one a minute) and republishes a pool whose global part differs from what it should be: new members in other pools, a pool back online, a pool that left the scope, or an edit made outside XO.
- **Sync cost** ([vdf#42](https://git.vates.tech/vates/vdf/issues/42), `sync-cost.test.mjs`, synthetic: one host per pool, every VM running with one VIF, a global configuration of 5 groups and 4 policies, agents answering at once, so XO's own work only). A pass scans every VM and composes every pool's document, and each pool's document carries the IPs of the members in the other pools, so the work grows with pools × members: 13 ms for 10 pools and 1,000 VMs, 0.14 s for 50 and 5,000, 0.5 s for 100 and 10,000, 2 s for 200 and 20,000, 7.5 s for 200 and 50,000 (one core of a laptop i7-1255U, Node 22). Under a steady flow of XAPI events that's a pass every 5 s. `VDF_SYNC_BENCH=1 node --test sync-cost.test.mjs` prints the table. The store is in memory there, its latency isn't measured, but the bytes a pass writes are: after a VM joins a group, 0.6 MiB at 100 pools and 10,000 VMs, 2.5 MiB at 200 and 20,000, 13 MiB at 200 and 50,000, nearly all of it the running VMs' records (key `vms`); each pool's `seen:` record is a few hundred bytes.
- **Storage:** XO's store (`getStore('vdf')`), key `global`: `{ document, revision, scope, publishedAt, publishedBy }`. Publishing with an older `revision` is refused. Key `syncs`: each pool's last write (shown as "Last sync"), so it survives a restart.

| Route                                       | What                                                                                                                                          |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /global`                               | The global configuration, each pool's sync state, and the members of global groups                                                            |
| `POST /global/actions/check`                | `{ policy, scope }`: every pool in scope checks its resulting document, nothing written; each one's own part comes back (`own`, vdf#27)       |
| `POST /global/actions/publish`              | `{ policy, scope, revision }`: check, then publish to every pool                                                                              |
| `GET /global/history`                       | The last published global configurations, oldest first, without their content                                                                 |
| `GET /global/history/{entry}`               | One of them (document and scope), with the one before it (`previous`)                                                                         |
| `POST /pools/{id}/actions/take_over_global` | `{ expectedOwner }`: make this XO the pool's owner for the global configuration, refused (409) if the owner isn't the one the user saw        |
| `POST /global/actions/take_over_replaced`   | `{ replaces }`: take over every pool the XO this one replaces owns (one `take_over_global` each), refused (409) if it replaces another XO now |

**VDF lock** ([vdf#41](https://git.vates.tech/vates/vdf/issues/41)): XAPI refuses to lock a VIF (`OPERATION_NOT_ALLOWED(A vswitch controller is active)`) while an SDN controller is registered on the pool, which XO's SDN Controller plugin does for Traffic Rules and Global Private Networks. XAPI still lets XO set the allowed addresses, so VDF enforces them itself on a VIF whose `other_config["vdf:locking"]` is `locked`; `locking_mode` is left alone (`xe vif-list` shows the VIF unlocked). XO's VIF edit locks as soon as it sets the allowed addresses, hence these routes:

| Route                                | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /vifs/{id}/actions/vdf_lock`   | `{ ipv4, ipv6 }`: single addresses per family, canonicalised (no prefix, unspecified, loopback, multicast or broadcast address, no IPv4-mapped or IPv4-compatible; IPv6 link-local taken; refused with 422 before any write). Sets the allowed addresses, then the key, then XO's IP pools; a step that fails undoes the earlier ones. Answers the VIF as XAPI has it afterwards. Refused (409) when the agent of the VM's host is stopped, older than VDF locks or on a host not running (for a halted VM: any host of its pool with a running agent), or XAPI locks or disables the VIF (decided on XAPI's record, not XO's object) |
| `POST /vifs/{id}/actions/vdf_unlock` | `{ clear? }`: remove the key (whatever XO's object shows), then with `clear` empty the allowed addresses: an agent never enforces an empty list                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Both need what XO's VIF edit needs to change a locking mode: `operate` on the VIF and on its network. A VDF-locked VIF counts as locked (its allowed addresses, trusted) only while its host's agent says it enforces it: the key is set, the host is running, its `vdf:status` is fresh (a heartbeat within twice its `heartbeatSec`, which must be given, and no more than a minute ahead of XO's clock) and not a stop status (`stopping`, written by an agent stopped cleanly), says `locking.vdfLock: true`, and lists the VIF in `locking.vdfEnforced` (the complete list of the VDF locks it enforces; an agent without that list is too old to vouch for any), and its `locking.vdfEnforcedAllowed[VIF]` (the addresses its gate enforces now) is the same set as XAPI's allowed addresses, compared canonically: a hung agent may still enforce the previous ones, given since to another VM. Otherwise the change is pending, and `vdf_lock`'s answer says `enforced: false`. `locking.vdfUnenforced` only says why one isn't. Otherwise it counts as an unlocked VIF: what its guest reports, untrusted. So a VIF just locked, hot-plugged, or on a VM that just migrated is untrusted until that host's agent lists it. A lock (XAPI's or VDF's) whose allowed list holds a prefix (the guest may use any address in it) or an unspecified, broadcast or multicast address (never a source, the agent's `specialAddr`) is untrusted too, whether XO or XAPI directly set it. An IPv6 link-local address (fe80::/10) may be listed, and `vdf_lock` takes one: the agent lets ND from link-local through from the VIF's own EUI-64 address only, so a guest using a random or stable-privacy one needs it listed. It doesn't make a lock untrusted, and it's never a member address: it's per link. Members across pools follow the same rule, from the status of each VM's host, and so does Trace. A pool XO can't reach keeps its members' last known addresses and trust (fail static), VDF locks included, until it's reachable again or its server is removed.

## Permissions

XO administrators can do everything. Other users, on a pool they have an ACL on, see its firewall (pool routes, with the `view` permission) and change the pool's own part (`check_policy` and `publish_policy`, with `administrate`); `GET policy` says whether they can (`canEdit`). The global configuration is for XO administrators only, as it applies to pools a user may not see: other users get it read-only from `GET /global`, with the pools and members they may view.

## History

XO keeps the last 50 published documents per scope (each pool, and the global configuration) in its store, keys `history:<pool id>` and `history:global`: `{ id, docId | revision, previousDocId, publishedAt, publishedBy, summary, document }`. `summary` counts the groups, policies and rules added, removed and modified, plus the size of the document (for a pool, its own part: the global part has its own history). The first pool publish also records what the pool held before (`publishedAt: null`), and the stored global configuration starts the global history. Publishing the same document again adds nothing. The pool history covers publishes made through XO's pool routes, what the global sync writes into the pool (`sync: { revision, times }`: successive syncs with nothing in between are one entry, its summary counting the pool's own part, usually unchanged), and the changes made outside this XO (below). So every version a pool held is there, and each entry has the version it replaced.

**Changes outside this XO** ([vdf#32](https://git.vates.tech/vates/vdf/issues/32)): another XO, `xe`, `vdf-agent publish`, or a copy of this XO may write a pool's document or its `vdf:global.owner`. XO keeps what it last saw in each pool (store key `seen:<pool id>`: the document's id, its global part's id and the owner, no document) and compares at each sync pass (XAPI events, at most every 5 s, and every minute, with or without a global configuration) and before each of its own writes to the pool. XO's cache of the pool follows XAPI's events, which arrive after a write returns, so what this XO writes (the document's id, the owner key it sets or removes) is recorded in that key as expected (`expect`, the latest 8 of each): a document or owner equal to one of them is this XO's own, whenever its event arrives. Any other difference is added to the pool's history as an entry with `outside: { seenAt, lastSeenAt, times, docChanged, globalChanged, ownerChanged, previousOwner, owner, sameIdentity }`: its document can be reviewed and restored like any other, `publishedAt` is when XO saw it (the write happened before), `publishedBy` is unknown, and the version it replaced is shown when this XO's history has it. `GET policy` and `GET /global` (per pool) report the last one as `outside`, with `current: true` while the pool still holds it.

- `sameIdentity`: another XO runs with this XO's identity, a copy of its whole data directory such as a cloned XO VM ([vdf#20](https://git.vates.tech/vates/vdf/issues/20)), which no import detects, or a tool keeps rewriting the pool. Said when the owner key was rewritten with this XO's id (a `since` this XO didn't write: only an XO writes that key), or when a change of the global part of a pool this XO owns keeps coming back after this XO wrote its own back (`times` > 1) with a global part of its own. A single change of the global part (`vdf-agent publish` of a local file, `xe`, a second XO publishing the pool's own part with the global part it last saw) isn't, nor is a local file without global part published again. The same change seen again only counts again (`times`), so two writers alternating add one entry.
- An owner that changed to another XO is a take over by that XO: the losing XO sees it there ([vdf#29](https://git.vates.tech/vates/vdf/issues/29) needs an alert on top).
- Limits: a change undone before the next pass (5 s) is missed. A write from outside supersedes this XO's pending writes (XAPI's events come in order), so a document or owner of this XO's coming back afterwards is an outside change too; only a write from outside that landed during one of this XO's writes, just before it, makes that write of this XO's show as an outside one. A change made while XO was stopped is seen at its first pass, unless the pool was never seen before. After an upgrade that teaches `publishedPolicy` a newer `vdf:policy*` key, a pool that already holds one shows its document id change once, as an outside change. Importing a config export keeps this XO's own `seen:*` records (the export's, older, would make every change since then look like an outside one).

XO 6 shows it in the Firewall's History tab, where a version can be restored as a draft, then reviewed and published like any edit.

## Config backup

The plugin registers a `vdf` config manager, so XO's config export (Settings > Config) includes the global configuration, the histories and the sync records, and importing it restores them (a loaded plugin reloads them at once), but not the exported XO's identity (see "A restored or copied XO" above). Pool documents live in the pools and aren't part of it. The manager is registered once per process, when xo-server registers the plugin, whether it's loaded or not: importing an export that has a `vdf` entry into an XO without this plugin fails, as for any unknown config manager.

## Requirements

Hosts run a `vdf-agent` recent enough to provide the `check`, `publish`, `stats` and `rule_log` plugin functions. A host whose agent doesn't is reported, not fatal.
